## Frame

Problem: Frame, Specify, and Design reliably govern artifact creation, but their semantic-analysis instructions are too thin for a bounded offline model to consistently recover intent, expose uncertainty, prove behavioral coverage, and scale design depth.

Desired outcome: The managed prompts provide a compact evidence-led analysis protocol and structured stage outputs that remain usable with a 64K context budget.

Actors: A software agent following the managed AEGIS payload, and the human reviewing its checkpoints and durable artifacts.

Primary scenario: A user supplies a software idea; the agent selects relevant evidence, separates stated and observed facts from inference and unknowns, captures a structured frame, derives complete verifiable behavior, and records a proportionate traceable design.

In scope: The canonical managed Frame, Specify, and Design prompts; the task, requirement, spec, and component templates needed to retain their outputs; focused structural tests and product documentation that directly describes the changed workflow.

Out of scope: Host-plugin mechanics, inference-runtime configuration, model selection, release packages, installation into other repositories, local-model execution, commits, and pushes.

Constraints: Preserve the six stages, existing checkpoints, EARS guidance, bounded `brief` resume, append-only rulings, stage reports, test seams, and current Git authority; use concise deterministic structures suitable for a minimum 64K context.

Success signals: Each stage defines an explicit analyze/challenge/write/audit sequence; material claims distinguish stated, observed, inferred, and unknown information; ambiguity cannot be silently converted into product behavior; Frame retains a durable idea record; Specify demonstrates coverage and concrete verification; Design scales with complexity and keeps canonical architecture current until validation.

Evidence: STATED - user approved the analyzed improvements, required `master`, and prohibited commit/push; OBSERVED - the current prompts emphasize workflow mechanics but provide only a short restatement, a mechanical behavior split, and a hard 30-line design; INFERRED - structured output and semantic self-audits will reduce omission and unsupported invention for offline models; UNKNOWN - model-specific compliance remains unverified because local-model testing is excluded.

Assumptions: The existing Markdown payload can carry the additional protocol without CLI schema changes; structural tests are sufficient for prompt-contract validation in this task.

Decision-blocking questions: None; the user accepted the proposed additions and supplied Git constraints.

Proposed behaviors: Frame captures a durable evidence-led idea record; Specify proves behavior coverage and verification quality without mechanical fragmentation; Design records proportionate requirement-linked decisions, risks, and proposed architecture without replacing current-state knowledge early.

## Design

- `[REQ-UX-81840102]` Add one compact shared analysis protocol in `AGENTS.md`: analyze evidence, challenge gaps, write the artifact, then audit it; require stated, observed, inferred, and unknown labels without requesting hidden reasoning.
- `[REQ-UX-81840102]` Add a durable `## Frame` scaffold to the task template and make Frame fill it before branch, journal-administration, or path-transition mechanics.
- `[REQ-UX-81840102]` Keep the existing checkpoint and path rules, but require evidence per quick-path criterion and label acceptance as scope rather than implementation.
- `[REQ-FUNC-aa60c372]` Make Specify build a behavior inventory and frame-to-requirement coverage table before creating files, then audit overlaps, conflicts, boundaries, and missing behavior.
- `[REQ-FUNC-aa60c372]` Replace the mechanical `and` split with independent variability and verification criteria; retain one-shall EARS guidance for final requirement prose.
- `[REQ-FUNC-aa60c372]` Give verification a setup, trigger, action, oracle, boundary, and automation model, and define deterministic spec-escalation conditions.
- `[REQ-FUNC-3e0263e7]` Treat 30 lines as a design default rather than a hard cap; require extra depth when interfaces, state, security, concurrency, migration, or operational risk demand it.
- `[REQ-FUNC-3e0263e7]` Cover requirement mapping, component ownership, interfaces, data/state, execution flow, failures, compatibility, observability, tests, risks, and open decisions where relevant.
- `[REQ-FUNC-3e0263e7]` Keep proposed architecture in the task design and update canonical current-state component knowledge at validate after code matches.
- Interfaces remain Markdown prompt and scaffold contracts; no CLI syntax or parsed journal fields change.
- Data remains plain durable files; the new Frame and coverage sections are human/model-readable and do not alter machine-readable headers.
- Test seams are three focused structural tests in `test_structure.py`, one per new requirement, plus the existing payload suite.
- Expected product files are `AGENTS.md`, steps 1-3 and 5, task/requirement/spec/component templates, `test_structure.py`, `CHANGELOG.md`, directly affected README, FAQ, prompt-cheatsheet, folder guide, and example-feature Markdown, plus the four matching PowerPoint companions.
- Rejected alternative: only lengthen each stage prompt independently; this would duplicate the evidence protocol, lose durable Frame data, and allow the three prompts to drift.
- No component architecture page is owed because this task changes workflow prose and scaffolds without changing the CLI or integration component shape.
