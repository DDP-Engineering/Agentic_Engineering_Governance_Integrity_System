# AEGIS Installation Payload and Configuration

This guide describes the installation layer of AEGIS. These artifacts install
the governance system beside an existing application; they do not describe or
replace the application's business code.

## What installation produces

WAEGIS copies the versioned AEGIS payload into the repository and generates the
repository-specific configuration from installation answers. It then writes an
installation manifest that records the completed result.

| Artifact | Represents | Data stored | Created or updated by | Why it is needed |
| --- | --- | --- | --- | --- |
| `.agentic/LICENSE.txt` | The license for the copied AEGIS payload. | Legal terms. | Copied by WAEGIS during installation or upgrade. | Keeps legal terms with the distributed material. |
| `.agentic/install-manifest.json` | Installation receipt and baseline inventory. | Payload and installer versions, installation time/mode, managed-file hashes and sizes, generated paths, skipped paths, payload digest, and the installation configuration snapshot. | Written by WAEGIS after deployment; amended by WAEGIS during supported configuration or integration changes. | Identifies exactly what was installed and detects payload drift without treating locally generated configuration as a generic copied file. |
| `.agentic/workflow.toml` | Live project-specific AEGIS policy. | Repository roots, component and report locations, traceability settings, adoption rules, gates, guardrails, and interface behavior. | Generated by WAEGIS from installation answers; thereafter maintained by the repository operator. | Connects the generic AEGIS engine to this repository and supplies the one policy source for CLI and hooks. |
| `.agentic/cli/` | Local AEGIS command-line engine. | Python package metadata and the executable AEGIS implementation. | Copied by WAEGIS from the selected payload version; replaced by supported upgrade/repair actions. | Lets the repository run a known local AEGIS version without relying on an undeclared global installation. |
| `.agentic/documents/` | Payload-local operator and reference documentation. | CLI reference, glossary, workflow/configuration guidance, invariants, and related operational material. | Copied by WAEGIS; updated with the payload version during upgrade/repair. | Provides documentation that matches the installed implementation. |
| `.agentic/tools/` | Shared helper launchers used by adapters. | Transport helpers, such as the Node launcher that invokes Python hooks. | Copied by WAEGIS; updated with the payload. | Keeps host-tool adapters small and gives them a common hook-launch contract. |
| `.agentic/hooks/` | Policy guard and evidence scripts. | Read/write guards, shell-write guard, secret scan, delivery preflight, evidence recorder, and configuration bootstrap. | Copied by WAEGIS; invoked by a loaded agent adapter. | Applies the configured AEGIS policy at tool-use time instead of relying solely on an agent to remember it. |
| `.agentic/integrations/` | Optional external-tool policy and connection configuration. | Integration-specific settings, for example an optional Repowise configuration. | Generated or updated by WAEGIS when the optional integration is selected; may be maintained by the operator within that integration's rules. | Keeps integration settings separate from the core workflow policy and payload code. |

The durable governance data created while people use AEGIS (requirements,
knowledge, components, reports, and run records) belongs to later guides. It
is deliberately separate from the installed engine and its configuration.

## The installation manifest

`install-manifest.json` answers two questions:

- What AEGIS material was installed?
- Which installation choices produced the local configuration?

| Field | Data stored | Populated by | Why it is needed |
| --- | --- | --- | --- |
| `manifest_version` | Manifest format version. | WAEGIS. | Allows tooling to interpret the manifest safely. |
| `product` | Product identity: AEGIS. | WAEGIS. | Prevents a manifest from being mistaken for another product's record. |
| `payload_version` | Installed AEGIS release. | WAEGIS. | States the behavior and documentation version deployed. |
| `installed_at` | UTC installation time. | WAEGIS. | Provides a durable deployment timestamp. |
| `installed_by` | Installer name and version. | WAEGIS. | Explains which deployment tool wrote the result. |
| `mode` | Deployment mode, such as `adopt`. | WAEGIS. | Explains whether the payload was applied to an existing repository or created with another workflow. |
| `files` | Each payload-managed path with `sha256` and `size`. | WAEGIS after copying the payload. | Creates a precise baseline for drift detection and upgrades. |
| `generated` | Paths generated from installation answers. | WAEGIS. | Distinguishes local configuration output from verbatim payload files. |
| `skipped` | Optional paths deliberately not overwritten. | WAEGIS. | Protects repository-owned or pre-existing material. |
| `payload_digest` | One digest representing the complete payload inventory. | WAEGIS. | Offers a compact integrity identity for the installed payload. |
| `configuration` | Installation-answer snapshot and generated-file hashes. | WAEGIS. | Preserves why the current configuration began in its installed form. |

### Configuration snapshot

`configuration.answers` records the choices made by the installer: source and
test roots, language, gates and commands, coverage settings, secret patterns,
scope/write/working-tree rules, alignment settings, and stage write access.

`configuration.generator_version` records the WAEGIS version that generated
configuration-driven files. `configuration.generated_files` stores a hash for
each generated file. `configuration.repowise`, when present, stores optional
Repowise source, profile, local endpoint, models, and enforcement mode.

WAEGIS writes this snapshot. It is needed as an audit trail for the deployment;
the live policy that AEGIS enforces remains `workflow.toml`.

## The workflow configuration

`workflow.toml` is the live configuration AEGIS reads. Its settings define:

| Configuration area | Data stored | Maintained by | Why it is needed |
| --- | --- | --- | --- |
| Root and quick-run settings | Schema version and optional changed-path quick-run behavior. | WAEGIS initially; repository operator afterward. | Defines the supported configuration format and optional reduced workflow. |
| Repository locations | Source, test, requirement, documentation, component, knowledge, and report locations. | WAEGIS initially; operator if repository layout changes. | Lets AEGIS find the material it governs. |
| Components, traceability, and adoption | Component baseline policy, language/file patterns, coverage scope, component-bundle rules, and adoption source-change policy. | WAEGIS initially; operator. | Defines how source maps to requirements, tests, and adoption readiness. |
| Alignment and interface behavior | Alignment rules, risk handling, form retention, and check-execution mode. | WAEGIS initially; operator. | Defines when work pauses for clarification and how workflow evidence is retained. |
| Quality gates | Build, type-check, lint, test, and security modes and commands. | Operator, normally with WAEGIS-assisted initial generation. | States exactly which deterministic checks AEGIS evaluates. |
| Guardrails | Secret patterns, protected paths, working-tree rules, write access, scope, and delivery control. | Operator. | Makes permitted actions and protected areas explicit for CLI and hooks. |

The detailed field-by-field `workflow.toml` reference will be moved from the
original combined note into this guide during the next installation-domain
editing step.

## Who owns what

- **WAEGIS** installs, upgrades, repairs, and generates the initial local
  configuration and manifest.
- **AEGIS** reads `workflow.toml`, runs the workflow, evaluates policy, and
  writes runtime evidence.
- **Repository operators and reviewers** decide the local policy and safely
  maintain repository-specific configuration after installation.
- **Agent adapters** invoke the shipped hooks and local CLI; they do not become
  a separate policy source.
