Analysis · AEGIS 0.13.0

How much does the workflow cost, and what does it buy?

A measurement of AEGIS overhead on three real repositories: the share of an agent's tool calls, tokens and git history that goes to the workflow, set against the defects the workflow demonstrably caught.

Date 2026-09-17 Hosts Claude Code, Codex Desktop Evidence 78 session transcripts, 3 git histories, 151 task journals, 1,111 requirement files
In one paragraph

Across three repositories and two hosts, AEGIS takes about a quarter of an agent's tool calls: 23 to 29 percent in Claude Code, 13 to 26 percent in Codex. The instruction text itself is cheap, around 4 percent of a turn's context. The cost is round trips: every check, summary, journal edit and requirement file re-reads the whole conversation. What the overhead buys varies sharply by repository. The one where the two-verdict review is run as written recorded 49 findings that sent work back to build. The two where it is not recorded one finding and none. Worth it for code that has to live, when the review is actually run. Not worth it for diagnosis, build and packaging work with no test seam, or a fix an existing requirement already covers.

Method and signals

Three repositories were measured, all governed by AEGIS 0.13.0 with explicit review enabled and two fix cycles. None is named here.

  • Repository A is a Python desktop application with a long history. It migrated from an earlier gate-based workflow in July, so its git churn is windowed to the AEGIS period and the removal of the old workflow's files is left out.
  • Repository B is an appliance with a Go core and a React interface, under AEGIS for its entire history.
  • Repository C is a fork of a twenty-year-old C and C++ open-source stack, where the agent's work is mostly cross-builds, packaging and hardware drivers rather than unit-testable features.

Every tool call in every transcript with at least 15 calls was classified by a script into nine buckets from the tool name and its input: AEGIS CLI run, instruction read, record read, record write, product read, product write, test or lint, git, other. Codex sessions were matched by working directory; subagent transcripts were excluded. The classifier is a set of regular expressions, so treat shares as accurate to a few points. Everything below is observed in files. Nothing is inferred from what the agent said it did.

Red · the row that matters

All three repositories have explicit review enabled with the same two fix cycles. Repository B recorded 49 changes_required verdicts across 45 journals. Repository A recorded one across 96, Repository C none across 10. A review that approves 95 of 96 candidates on the first pass is not reviewing. The session study below shows the mechanism: the agent records both verdicts as approved without running two separate passes, and the advisory check has no rule that notices. In Repository A the overhead of the review stage was paid and its benefit was not collected.

Orange · Repository A is a fix factory

Ninety-three journals opened in August alone, 59 of them fixes, and only 15 took the quick path. A fix per journal is where a 25 percent bookkeeping-only commit rate comes from: each small change pays a frame, a build red line, a validate pass and a close-out commit. That cadence would suit the quick path more often, or one journal per batch of related fixes.

Orange · Repository C is the wrong shape for test-first

Cross-builds, packaging and a USB protocol have no unit-test seam, so nine of 27 requirements are verified by hand and 13 requirement files already point at stale paths. AEGIS still produced a usable audit trail, which the repository's own readme names as the point, but the build stage's red-then-green rule became a manual observation a third of the time. The lowest Codex share, 13 percent, is consistent with that: fewer stage transitions because there was less to prove.

The two hosts spend the overhead differently

Claude Code runs the CLI and writes records: in Repository A, 7.8 percent of its calls are aegis.py runs and 11.3 percent are journal or requirement writes. Codex on the same repository runs the CLI in 1 percent of calls and instead reads records in 21 percent of them. Same share, opposite mechanism. A rule added to check reaches the first host on every transition and the second only when a human runs it.

One session, both ways

One Repository A session lasted just under two hours and ran the same problem both ways. The first six user turns asked why a hosted model provider returned a differently shaped answer than local models for a text-splitting step, and how to skip a refused chunk while preserving resume. The operator's words were "do not use aegis, just answer". The seventh turn chose an option and said "implement this on master branch, using aegis. Do not commit."

The 44 workflow calls split into 19 CLI runs, 16 reads and writes of journal and requirement files, and 9 reads of the contract and step files. The stage went frame → specify → design → build → validate → deliver on the full path in autopilot, and produced one journal of 434 lines, four requirement files, one reconciled knowledge page and a changelog entry.

What it caught

Green · build, red then green

The first green run exposed a completion defect the design note had not named. The journal records it in one line, with the command and the exit code.

Green · validate, diff review

A second call path in the chunk-regeneration function was found to bypass the new guard. Fixed in stage.

Green · validate, two-verdict review on the rerun

The specification-compliance pass found that a second, unguarded provider call on the ambience path would still end the run on the operator's own project settings. The implementation-quality pass found skipped chunk ids seeded from a snapshot the resume logic had already discarded. Both were fixed and regression-tested, red without the guard and green with it.

What it did not do on its own

Red · the review was stamped, not run

The round-one verdicts were first recorded as approved without the two passes being run separately. The operator asked "did you run the 2 separate validators?", the agent withdrew the verdicts, reran both passes and only then found the ambience defect. This is the same mechanism the cross-repository table shows at scale: one changes_required in 96 journals.

The strict full check was skipped as well, and said so:

DEVIATION build: ran the targeted modules instead of the 63-file impacted set — the user limited verification to targeted tests and will exercise the app by hand

This is the advisory design working exactly as documented. Nothing blocked the shortcut, the journal made it visible, and a human had to insist.

Why two verdicts and not one

The implementation-quality pass inspects the code the agent wrote, and by that standard the ambience path was invisible because the agent had not touched it. The specification-compliance pass reads the requirement, here "continue through the last chunk", and asks what the whole loop must do. A single merged review inherits the design's framing of where the seam is, which is precisely how the defect survived the first round.

What the overhead bought, where it was collected

Repository B is the one where the workflow was run as written, so it is the honest measure of the upside. Counted from its 45 journals, not from prose:

  • 309 red-then-green lines with command and exit code. The test-first rule was followed, not narrated.
  • 49 changes_required verdicts and 27 returns to an earlier stage. Findings were fixed under proof rather than patched in place.
  • One task ran five review rounds and ended blocked, with concrete findings each round: a rate cap instantiated per interface so the documented global bound multiplied, a label test that decoded a second in-memory object instead of the emitted artifact, an audit-outbox retry with no automated oracle. A green suite does not reveal those.
  • 159 deviation notices, 20 of them tool noise. The rest name narrowed verification, skipped checks and accepted warnings, which is the point of the notice.

Repository A collected the build-stage benefit, 89 red lines and a low noise rate, and almost none of the review-stage benefit. Repository C collected an audit trail and little else that a test could prove.

Journals, requirements and knowledge together are half the product-source churn in Repository B, which agrees with the tool-call share once tests are counted. The fingerprint JSON is a different matter. It exists only to feed the evolution report, it is the largest single line of churn in Repository B's history, 48,000 lines in Repository A's AEGIS period and 69,000 in Repository C's, and no reader ever opens it. It is the one pure-noise item in all three repositories.

Two secondary costs are visible in the records. Repository B's journal logs have a median of 28 entries and a maximum of 227, which is why the current rules consolidate inner-loop retries. And every repository's advisory check carries warnings today, so the bookkeeping drifts between tasks:

Verdict

Use the workflow when the code has to live, and run the review

  • A feature on a codebase you will still be changing in six months.
  • Anything with a data format, a permission rule, a resume contract or an error path a user will hit.
  • Any session where nobody will personally read the whole diff. The requirement text is what gave the review a reason to look outside the code the agent wrote.
  • Only when the two-verdict review is actually run as two passes. Repository A paid for the stage and collected one finding in 96 tasks.

Leave the agent alone when

  • The ask is diagnosis or explanation. The first hour of the session above was correctly run without the workflow.
  • The change is one file and an existing requirement already covers the behavior. That is what the quick path is for, and Repository A used it for only 15 of 59 fixes.
  • The work is a cross-build, a package or a driver with no test seam. Keep the journal for the audit trail if the record matters, but do not expect test-first to mean anything there.
  • The code is exploratory or throwaway and will not be validated or delivered.

Four changes that cut the cost or collect the benefit

  1. Make the two-verdict review non-skippable in practice. A strict check finding when a validate stage report carries approved verdicts with no per-verdict log line. This is the only change that turns Repository A's red row green, and it costs nothing in tool calls.
  2. Stop committing anchor and evolution JSON. Ignore the files, or have evolution write a short added, modified and removed summary into the journal. This removes the largest line of churn in all three histories.
  3. Autopilot by default for trusted tasks. Checkpoint stops are what push a session from the 25 percent middle to the 45 percent tail, and the pre-publication approval remains in both modes.
  4. Batch small fixes under one journal, or take the quick path more often. One journal per fix is what gives Repository A a 25 percent bookkeeping-only commit rate. The quick path was designed for exactly that cadence and was used a quarter of the time.
